# Holt 对照与可纠正记忆（2026-09-28）

## 共同思想与区别

本轮参考本地 `/root/project_job/others/holt` 的 README、`src/wiki.ts` 和记忆命令实现。Holt 将本地可见的事实作为长期知识，并保留原始对话；它的 wiki 页是带 `sources` 的派生视图，可以从事实重建。`facts.md` 可读可改，但 README 明确提示直接改文件不会生成语义索引，建议通过 `holt memory add` 写入。它还提供记忆图和按工作目录隔离的记忆。

Memoria 当前的可靠来源是 SQLite 中的结构化记忆及替代链，`MEMORY.md` 是可重建投影。此前 Dashboard 能看替代时间线、撤销后台抽取，但缺少面向单条记忆的显式纠正流程；旧的 PATCH 原位改写正文，审计链会断。两者都重视“用户能看见记忆”，Memoria 本轮聚焦“用户能指出错误、保留旧版并恢复”。未引入 Holt 的 wiki 或目录隔离机制。

## 本轮实现

1. `POST /api/memories/{id}/correct` 要求新内容、类型、重要度和纠正原因。数据库事务同时写入新版本、停用旧版本、保存 `correction` 替代边；并发替代返回 409，空原因或无变化返回 422。
2. 同步更新 FTS 和可用的向量索引；embedding 服务不可用时仍可纠正，后续可回填向量。`MEMORY.md` 从有效记忆重新投影，旧版本退出对话召回。
3. 历史 PATCH 改为同样保留旧版本，返回新 ID。`/timeline` 增加关系类型和来源引用，响应仍隐藏 embedding。
4. Dashboard 的“检查并纠正”窗口显示来源、完整版本链、纠正原因和显式表单。点击记忆卡片即可打开窗口并聚焦编辑区；“填入此版本”只预填历史内容，用户确认保存后生成又一个新版本。
5. 自动 consolidation 在命中用户纠正版本且计划 supersede 时跳过自动替代，要求再次人工检查。这个保护依赖候选匹配和模型判断；对完全不同表述造成的独立冲突，仍需后续冲突评测。后续已新增所有对话提取候选的审核队列，见「自动记忆审核与来源定位」。

## 行为边界

- 纠正是版本替换，不修改原始会话消息，也不改变 `SELF.md`。
- 永久删除仍会删除记忆行，时间线可能缺少已删除版本；需要保留审计时应使用纠正或版本恢复。
- 记忆卡片中的 `source_ref` 后续已接通原始会话跳转；原始会话被删除时无法再定位。
- Holt 的 wiki 派生页重建思想可用于以后做用户资料页，但必须先确保来源可见、错误可纠正，再增加自动综合层。

## 验证

运行 `python -m pytest -q`、`cd frontend && npm run build && npm run test:e2e`。回归覆盖纠正后旧版退出召回、纠正原因与关系保留、重复或过期版本拒绝、从历史正文恢复，以及前端操作链。
