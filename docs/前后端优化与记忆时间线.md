# 前后端优化与记忆时间线（2026-09-28）

## 审查范围与取舍

本轮检查了 `frontend/src`、`memoria/api`、`memoria/store.py`，并重点阅读本地 `others/akashic-agent` 的聊天界面、Proactive 和 Drift 手册，以及 `others/claude-mem` 的搜索与渐进式上下文说明。借鉴的是交互和运行机制，没有复制上游界面或源码。

| 位置 | 发现 | 本轮处理 |
|---|---|
| 前端导航 | 移动端有五个页面入口，但布局只设四列；服务状态固定显示“在线” | 改为五列导航；状态由 overview 请求决定 |
| 前端请求 | 一个聚合请求失败会令 `Promise.all` 整体失败，其余成功数据也无法显示 | 改用 `Promise.allSettled`，各面板独立更新并报告首个错误 |
| 前端视觉 | 聊天与运维页层级较平，空状态缺少可点击的起点 | 统一暖色背景、深色侧栏、青绿重点色、卡片间距和聊天建议；移动端保留清晰入口 |
| 前端输入 | 中文输入法选词时按 Enter 可能触发发送 | 组合输入期间不触发 Enter 发送 |
| 记忆 API | `/history` 只能看到与单个版本直接相连的一条边，前端也没有版本视图 | 新增完整替代链 `/timeline`；前端点击时按需加载 |
| Drift 后台 | 每轮有审计摘要，但下一轮没有明确的同技能接续信息 | 从同技能最近一次已完成运行读取限长摘要；失败或其他技能的记录不注入 |

## 从参考项目落地的机制

**Akashic Agent** 的聊天界面把桌面会话导航、移动端入口和回复区域分别处理；其 [Drift 指南](https://github.com/kachofugetsu09/akashic-agent) 用接续点保持技能跨轮上下文。本轮落实前端导航和连接反馈，并让 Memoria 的 Drift 从同技能最近一次已完成运行读取最多 800 字摘要。摘要被标注为参考材料，不改变工具白名单或预算。其 Proactive 机制强调 source、判断与投递的职责分离；订阅源投递仍需要独立的事件去重、ACK 和用户触达设置。

**Claude-Mem** 的 [渐进式搜索流程](https://github.com/thedotmack/claude-mem#readme) 先展示紧凑结果，再按需读取时间线与正文。Memoria 现有替代记录适合先做一个较窄的落地：记忆列表只显示当前摘要，点击一条记忆后才请求完整版本时间线。时间线展示旧版和当前版、创建时间、来源及替代原因；它是**记忆替代链**，不是会话消息时间线。

后端用递归查询沿 `memory_replacements` 向前和向后找相连的版本，并以 `UNION` 去重，最多返回 100 个现存记忆版本。API 响应模型排除 embedding。永久删除的版本仍可能留在审计边表，但没有记忆行，故不会显示为版本卡片。

## 后续优化建议

1. **P0：前端可维护性。** `main.tsx` 仍把会话、记忆、追踪、工具和设置放在一个文件；拆成页面和数据 hook，再让各页面独立加载并处理错误。当前 `Promise.allSettled` 解决了部分失败导致整页丢数据，但每次刷新仍请求所有页面的数据。
2. **P1：Drift 结构化接续。** 本轮只有上次完成摘要。后续可参考 Akashic 的 `skill_continuum`，为允许跨轮的技能记录最后处理的对象 ID、阶段和显式暂停状态，并验证失败重试和幂等边界。
3. **P1：主动信息源。** 参考 Akashic 的 `alert/content/context` 区分和投递后精确 ACK，先做只在 Dashboard 展示的待审建议，再接用户授权的外部通道。
4. **P1：上下文成本。** 参考 Claude-Mem 的分层获取，量化 `recall_memory` 返回正文的 token 成本；再设计紧凑索引与批量详情接口，并用现有评测集核对召回率。
5. **P2：性能与可访问性。** 长会话列表按需加载，运维表格提供窄屏卡片视图；对慢接口增加加载占位和局部重试。完成实际设备与键盘导航检查后再扩展动画。

这些建议按 Memoria 当前单用户、SQLite、本地 Dashboard 的边界排序，不预设要移植两个项目的完整插件体系。
