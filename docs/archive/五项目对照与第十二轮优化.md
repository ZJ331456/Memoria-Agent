## 本轮落地：长问题的关键词候选召回

原流程在无向量索引时只预取按重要性排序的前 200 条，再尝试用整个查询句子做 FTS 短语匹配。用户问“周末徒步安排”，存储内容为“我喜欢周末徒步，经常去山里”时，整句不会命中；若这条低重要性记忆排在第 200 条之后，就无法参与后续词面评分与 RRF。

现在 `Store.keyword_memory_candidates` 保留整句精确匹配优先级，同时从英文词和连续中文三字片段构造受限的 FTS `OR` 查询，合并去重后交给现有召回排序。旧版 SQLite 若只能使用默认 FTS 分词器，则对这些片段使用受限的 SQL 子串扫描作为兼容回退。检索片段会去掉末尾的“是什么”，避免这类通用问法挤占具体线索的排序。只检索 active 记忆；空查询直接返回空集；候选上限不变。短于三字符的片段仍依赖现有精确匹配、近邻预取或向量召回，因为 SQLite trigram 无法索引它们。

回归场景：先存 1 条低重要性偏好，再存 220 条高重要性无关记录。在不使用 embedding 的情况下，无论是 trigram 还是默认 FTS，新流程都把目标记忆排到第一位；精确匹配仍优先，已 supersede 的旧记忆不会返回；“十月的运动目标是什么”仍把马拉松目标排在 Rust 目标之前。运行方式：

```bash
python -m pytest -q tests/test_memory_retrieval_scale.py
python -m eval.run_seeded --min-recall 0.75
python -m pytest -q
```

这只是一个确定性缺口的修复。12 条种子集主要覆盖小规模召回，不能据此推断真实用户数据上的总体准确率；长问题里没有任何与记忆重合的词时，仍需要向量召回或查询改写。

## 下一步优先级

1. **检索质量 P0**：把匿名真实失败案例按无向量、有向量、100/1,000/10,000 条记忆分层；报告 Recall@K、错误注入率、P95 延迟和 prompt 字符数。设定回归门槛后再调 RRF 权重、实体或时间信号。
2. **记忆可信度 P1**：给召回项展示创建时间、来源、替代链和“当前/历史”状态；针对“现在/当时/下周”问题引入明确的时间解释，避免把旧事实当当前事实。
3. **主动触达 P1**：沿用 Drift 的预算、静默时段和审计方式，另建订阅源与消息投递状态机。先做仅在 Dashboard 展示的建议，再接外部通道。
4. **上下文成本 P2**：测量记忆注入的 token 占比；按需展开详情、时间线及来源，减少重复正文注入。
5. **目标与技能 P2**：把目标进展做成可编辑的状态记录，技能路由引入可解释的匹配分数和回归集。

优先级顺序依据当前代码缺口与可验证性，不代表五个参考项目的功能可以直接移植。尤其主动触达与目标自动修改需要独立的用户控制和回滚能力。
