# Memoria-Agent 项目规划说明书

本文是当前版本的实施规划。最初的完整方案保存在[项目初始蓝图](./archive/项目初始蓝图.md)；现行代码边界见[系统架构](./系统架构与实现说明.md)，接口见[API 文档](./API接口文档.md)，评估方法见[评估说明](../eval/README.md)。

## 1. 项目定位

Memoria-Agent 的重点是让长期记忆可检查、可纠正、可追溯，并让多个 Agent 在明确授权的空间内共享经过审核的记忆。聊天界面是使用这些能力的入口之一。

当前由两个边界清晰的部分组成：

- **个人聊天运行时**：会话、工具调用、个人记忆检索、后台候选提取与人工审核。
- **共享记忆治理服务**：Agent key、空间角色、提案审核、版本、有效期、撤销和事件记录。

共享服务已有独立 API 与前端工作台；旧聊天运行时还没有 `agent_id + space_id` 上下文。现阶段只能声称共享记忆服务按空间隔离，不能声称整个聊天系统具备多 Agent 身份隔离或跨 Agent 自动协作。

## 2. 当前能力与边界

| 领域 | 已实现 | 当前边界 |
| --- | --- | --- |
| 对话运行时 | FastAPI、SSE 流式响应、会话压缩、工具循环、取消和 Turn Trace | 本地个人数据域；未从共享空间取回记忆 |
| 个人记忆 | 关键词与可选向量召回、版本化纠正、来源消息定位及来源级撤销 | 自动提取只生成待审候选，批准前不参与召回 |
| 共享治理 | Agent key、私有/共享空间、reader/contributor/curator/owner 角色、提案审核、版本 CAS、过期与撤销 | 权限由 `MemoryGovernance` 和 `/api/shared/*` 执行；不是多用户 SaaS 隔离 |
| 扩展与后台工作 | Tool Search、轻量 Skills、MCP 客户端、受约束的 Drift | Drift 在后台整理，不向用户主动推送消息 |
| 评估 | 个人检索小型回归、24 条共享治理合成案例、本机 SQLite 性能脚本 | 尚无公开治理数据集的正式成绩；本机延迟不是线上 SLO |

个人记忆与共享治理使用不同的数据表和认证入口。共享层的 `source_ref` 是来源指针，不自动证明外部材料真实，也不授予读取旧个人会话的权限。共享层的角色授权不能替代旧 `/api/memories` 和来源消息路由的身份设计。

## 3. 优先路线

### P0：巩固治理正确性与审核体验

目标是让写入、变更和删除都能被用户理解并复核：

1. 保持个人自动提取的候选队列与有效记忆分离；完善跨页筛选、待审数量、来源失效提示和冲突反馈。
2. 在共享空间中维持“提案 → owner/curator 审核 → 有效版本”的流程；新增版本必须明确展示被替代版本与审核理由。
3. 对内容、类型、来源、有效期等变化继续要求当前版本 ID 的 CAS 校验；审核时重验提案人授权，避免旧权限或旧版本被复用。
4. 对撤权、过期、撤销和私有空间的检索、已知 ID 详情、版本链与事件读取保持一致的访问边界。
5. 分别整理个人来源消息与共享治理事件的回放链路；明确哪些正文只对 owner/curator 可见，避免跨数据域误授权。

治理状态的检查重点：

| 对象 | 合法流转 | 不允许的捷径 |
| --- | --- | --- |
| 个人自动候选 | 待审 → 批准或拒绝 | 待审时写入有效个人记忆 |
| 共享提案 | `pending` → owner/curator 批准或拒绝 | contributor 直接发布、reader 提案 |
| 共享有效版本 | 新版经 CAS 审核后替代旧版；到期或撤销后停止普通读取 | 用旧版本 ID 覆盖现行版；按已知 ID 读回失效正文 |

这里的“到期”是查询时计算的有效状态，不能把过期时间误写成一次人工审批事件。事件记录支持追溯，但数据库管理员仍有底层访问能力，不能把它描述为防篡改存储。

验收：授权成员能获取已批准且有效的内容；未授权或撤权成员经搜索和已知 ID 查询都不能读取受限正文；冲突提案不能静默覆盖；候选不经批准不进入召回。每项均以 API 回归和前端操作检查验证。

### P1：让聊天运行时安全使用共享记忆

此阶段尚未实现，应先设计身份流与权限检查，再接入共享召回：

1. 为每次聊天请求、工具调用和来源读取建立显式的 `agent_id + space_id` 上下文，并约定上下文如何从可信认证入口产生。
2. 将可读空间筛选放在检索之前；召回结果必须保留空间、版本、来源与有效期，以便回答引用和审计。
3. 将聊天中产生的共享候选提交为提案，等待授权审核；模型或工具不得绕过审核直接发布共享记忆。
4. 明确个人记忆、团队共享记忆、私有空间记忆之间的写入与读取策略，并为跨空间引用、来源跳转和撤权后的会话历史制定规则。
5. 完成端到端授权测试后再把“多 Agent 共享记忆”描述为聊天运行时能力。

建议按以下顺序集成，以便每一步都能单独回滚和验证：

- 先在 API 入口绑定可信 Agent 身份，不接受模型或前端随意指定任意 `agent_id`。
- 再为聊天检索增加只读的授权空间过滤，并在 trace 中记录选择的空间与记忆版本。
- 最后开放共享提案提交和来源跳转，每个输出路径都补上撤权后的访问测试。

阶段门槛是跨空间信息不能经搜索、已知 ID、工具结果或流式片段旁路流出。未满足门槛时，工作台仍可独立使用共享治理服务，但聊天链路不接入共享数据。

验收：同一问题由不同 Agent 和空间上下文发起时，只召回各自可读的有效版本；已知 ID、来源跳转、工具参数与流式输出都遵守同一权限。撤权后新请求立即失去相应空间的读取能力。

### P2：扩大评估与运行可靠性

1. 收集经匿名化的真实审核与检索失败案例，固定独立留出集，并统计授权召回、越权泄漏、冲突审核、生命周期和来源定位。
2. 研究 GateMem、LongMemEval 或 LoCoMo 中适用的固定子集与适配规则；实际跑通前不引用其官方成绩。
3. 在容量增长前设计索引、分页、迁移、备份恢复与多实例写入策略，并记录测试机器、规模与工作负载。
4. 将审核耗时、待审积压、撤权事件、检索延迟与失败原因纳入可观察指标；分别报告本机存储延迟和真实 HTTP/模型链路延迟。

验收：评估脚本从实际系统生成预测，不从预期答案复制；报告注明数据来源、时间、环境和边界。备份恢复与迁移通过可重复演练验证，性能结论只对应测过的负载。

评估扩展应保留三份互不混淆的报告：治理规则的确定性回归、真实任务中的回答与引用质量、指定负载下的性能。真实失败案例进入固定回归后，新增案例和用于调整实现的案例也应分开，避免只对已见问题调参。

## 4. 评估与发布口径

| 证据 | 可说明什么 | 不能说明什么 |
| --- | --- | --- |
| 个人检索种子案例 | 固定小样本上的召回回归 | 真实长期使用中的记忆质量 |
| 24 条共享治理合成案例 | 授权、隔离、生命周期、决策与来源链路的确定性回归 | GateMem、LongMemEval、LoCoMo 等公开集成绩 |
| 本地共享记忆性能脚本 | 指定 Python/SQLite 环境下的初始化与查询耗时 | 含 HTTP、模型、网络和并发负载的线上 SLO |
| 浏览器回归 | 指定流程可由用户操作完成 | 全部权限组合或大规模负载正确性 |

验收结果要同时说明功能是否通过、哪些真实场景尚未覆盖，以及测量环境。准确率、延迟和案例数量应从当前实际报告引用，不能沿用历史轮次中的过时数字。

从仓库根目录执行基础检查：

```bash
python -m pytest -q
python -m eval.run_governance --min-pass-rate 1 --max-leak-rate 0
python -m eval.benchmark_shared_memory --memories 100 --spaces 5 --queries 30
npm --prefix frontend run build
npm --prefix frontend run test:e2e
```

基准脚本只使用临时 SQLite 和本地调用；浏览器回归需要前端依赖与 Playwright 浏览器已安装。完整参数、指标定义和历史实测报告见[评估说明](../eval/README.md)。

每次发布或对外展示结果时记录：

- 对应的代码提交、案例版本、运行命令与测试通过情况。
- 被测路径是个人记忆、共享治理 API，还是尚未接入的聊天与共享组合路径。
- 有效样本数、授权召回和越权泄漏等指标的分母及失败案例。
- 性能运行的机器、Python/SQLite 版本、记忆数、空间数、查询数和并发条件。

缺少这些条件时，数字仅能作为开发时的局部观察，不能作为公开基准或线上保证。

## 5. 明确保留为计划的方向

Telegram、QQ、飞书、CLI 等外部通道，主动向用户投递消息，动态插件加载与市场，跨 Agent 自动编排，以及多用户 SaaS 隔离，均不属于当前已完成的运行链路。是否实现应由实际使用场景、身份和授权模型、运维成本共同决定；不能因[原始蓝图](./archive/项目初始蓝图.md)列出了目录或里程碑，就把它们写成现有功能。
