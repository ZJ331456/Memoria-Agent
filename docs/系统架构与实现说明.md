# Memoria-Agent 系统架构与实现说明

本文描述当前实现；文档入口见[文档导航](./README.md)，HTTP 参数见[API 接口文档](./API接口文档.md)。早期逐轮审计已移至[历史归档](./archive/README.md)。

## 1. 文档结论

参考 `akashic-agent` 的真实代码后，完整 Agent 系统可拆为 **8 个部分**：配置与启动、消息与会话、Agent 推理、长期记忆、工具与插件、主动触达、通道接入、Dashboard 与可观测性。

本仓库已实现本地聊天、个人记忆审核与纠正、工具调用、受预算约束的空闲 Drift、工作台和独立的共享记忆治理服务。Drift 是后台整理，不会自动向用户外发消息；外部通道、主动推送、动态插件市场仍未接入。共享服务按 Agent key 和空间授权运行，但旧聊天 runtime 尚未使用这一身份上下文，因此不能把整个聊天系统视为多 Agent 隔离运行时。

```text
Browser / Dashboard → FastAPI
                      ├─ AgentService → AgentRuntime → 个人 memories / sessions / jobs / reviews
                      │                   └─ LLMClient → OpenAI-compatible API
                      └─ MemoryGovernance → agents / spaces / proposals / governed_memories
                                      SQLite Store；个人检索可选 sqlite-vec
```

## 2. 第一部分：配置与启动

### 2.1 参考项目做法

`akashic-agent` 由 `main.py` 解析命令，再由 `bootstrap/app.py` 和 `bootstrap/tools.py` 分成应用运行时与核心运行时两层装配。这样通道、Dashboard、后台任务的生命周期由应用层管理，而模型、会话、记忆和工具由核心层管理。

### 2.2 Memoria 实现

- `main.py`：解析 `--config`、`--host`、`--port` 并启动 Uvicorn。
- `memoria/config.py`：读取 TOML，解析 `${ENV_VAR}`，支持 `extends` 配置继承。
- `config.toml`：本机实际模型配置，已被 Git 忽略；`config.example.toml` 是不含密钥的独立模板，不引用其他仓库。
- 配置优先级：命令行指定文件 > `MEMORIA_CONFIG` > `config.toml` > `config.example.toml`。

系统使用三类模型：

| 模型 | 作用 | 当前配置来源 |
|---|---|---|
| main | 最终对话生成 | `[llm.main]` |
| fast | 低成本记忆提取 | `[llm.fast]`，缺失时回退 main |
| embedding | 语义召回、向量回填和重复抑制 | `[memory.embedding]` |

安全边界：`Settings.public_dict()` 只向 Dashboard 返回模型名、Base URL 和是否已配置，永不返回 API Key。

## 3. 第二部分：消息与会话

### 3.1 设计职责

会话层负责把不同来源的连续消息组织成上下文，也是记忆 consolidation、主动推送和审计回放的基础。参考项目中它由 `session/manager.py`、`session/store.py` 和消息总线共同承担。

### 3.2 当前数据模型

`sessions` 保存会话标题和时间；`messages` 保存角色、正文和所属会话。SQLite 开启 WAL 与外键，删除会话时级联删除消息。

关键约束：

- 会话首次发送消息后，标题自动取用户消息前 28 字。
- 发送前先持久化用户消息；模型失败时用户输入仍保留，便于重试和排障。
- 只向模型发送 `memory_window` 范围内的最近消息，避免上下文无限增长。
- 所有时间使用带时区的 UTC ISO 8601 字符串。

## 4. 第三部分：Agent 推理核心

### 4.1 参考项目链路

`akashic-agent` 的被动回复包含 BeforeTurn、BeforeReasoning、PromptRender、Reasoner、AfterReasoning、AfterTurn 等 Phase，并允许插件插入模块。完整实现适合扩展型运行时，但 MVP 首先需要保证核心数据流正确。

### 4.2 当前链路

```text
POST chat
  → 校验会话
  → 保存 user message
  → 记忆检索门控；需要时执行关键词/向量召回并用 RRF 融合
  → 拼装 system prompt + memory context + recent messages / 压缩摘要
  → 调用 main model，按授权执行工具循环
  → 保存 assistant message
  → 以用户消息 ID 排入后台抽取任务，记录 trace 并返回回复
  → worker 后续用 fast model 提取候选，存入 memory_reviews
  → 用户审核批准后才调用 MemoryEngine 写入有效个人记忆
```

`memoria/llm.py` 直接调用 OpenAI Chat Completions 兼容接口。请求超时由 `[llm].request_timeout_seconds` 控制，默认 90 秒；供应商错误分类后由 API 返回对应错误，前端显示错误信息。不同兼容服务的工具调用和流式响应仍需单独验证。

当前已实现 `ToolRegistry`、结构化 tool calls、最大迭代数、重复调用保护、写工具授权、输出裁剪、SSE 流式响应和 turn 取消。

## 5. 第四部分：长期记忆

### 5.1 参考项目的双层记忆

`akashic-agent` 同时使用人类可读的 Markdown 层与 `memory2` 语义层。Markdown 包括 HISTORY、PENDING、RECENT_CONTEXT、MEMORY 等文件；向量层包含 query rewrite、HyDE、retriever、dedup、profile extractor 与 post-response worker。

### 5.2 当前 MVP 策略

当前 `memories` 表保存：正文、类型、重要度、来源、时间、embedding、状态、强化次数和被替代关系。旧数据库启动时会自动迁移缺失列。安装可选依赖后由 sqlite-vec 执行 cosine KNN；未安装时有上限地扫描 JSON embedding。记忆类型包括 fact、preference、profile、goal、procedure。

检索包含关键词和向量两条通道：中文二元词组/英文词元形成关键词排名，embedding 余弦相似度形成语义排名，再通过 RRF 融合。每条内部结果带通道名次和相似度，模型不可用时自动回退关键词通道。

每轮回复后，后台 worker 用快速模型按严格 JSON 约定最多提取三条候选，并遵循以下规则：只记未来有帮助的用户信息，不记临时问题，不记凭据，不把助手内容当用户事实。候选先进入 `memory_reviews`；用户核对来源，可修改或拒绝。批准后才进行一致性判定：重复事实强化，明确变化的偏好/画像/目标/流程替代旧版本，独立信息另行创建。未批准候选不进入召回或 `MEMORY.md`。详见[自动记忆审核与来源定位](./自动记忆审核与来源定位.md)。

自动抽取由可重试后台任务执行；已批准的替代版本可按来源预览撤销并恢复旧版本。个人记忆的来源定位、纠正与共享空间的提案审核属于两套边界，分别使用原有个人 API 和独立的 `/api/shared/*`。

## 6. 第五部分：工具与插件

参考项目的插件能通过 PhaseModule、EventBus、tool pre-hook 和工具注册介入运行时，并带有依赖排序和失败回滚。

Memoria 按以下边界分层；当前具备轻量 Pipeline、进程内 EventBus、工具权限策略与 MCP 客户端，动态插件发现与装卸仍是扩展点：

- `ToolRegistry`：工具 schema、执行器、权限级别、超时和结果裁剪。
- `Pipeline`：按阶段与优先级运行已注册的生命周期处理器，目前没有依赖拓扑解析。
- `EventBus`：在进程内分发观察事件，监听者失败不会改变主链路状态。
- `ToolPolicy` / `ToolAuthorization`：限制高风险工具和单工具写权限。
- `PluginManager`：manifest 发现、动态加载、失败回滚和禁用仍属计划。

当前已经具备 read-only 与可撤销写工具、递归 schema 校验、超时/输出上限、精确到工具名的写授权，以及重复调用保护。插件发现和动态装卸保留为后续扩展边界，不影响核心工具闭环。

## 7. 第六部分：主动触达

参考项目的 `proactive_v2` 是独立循环：根据 presence/energy 动态决定轮询间隔，读取 alert、content、context 三路来源，再经 gate、judge、resolve、deliver；无内容时可以进入 Drift 执行 SKILL.md。

面向用户的主动推送若实施，需要具备：

- 独立于聊天请求的 asyncio 后台循环。
- 每个目标单独的冷却时间、静默时段和预算。
- 数据源游标与内容去重，避免重复推送。
- 判定 trace，能够说明为何发送或跳过。
- 发送与决策分离，发送必须经过通道权限检查。
- 现有 Drift 已限制技能、步骤数、写工具白名单、静默时间和日预算，可复用这些约束。

当前可配置的 Drift 只在空闲时整理并记录结果，不实现订阅源判断后的对外投递。主动触达尚未启用，防止未经用户设置目标和静默时间就产生外发行为。

## 8. 第七部分：通道接入

参考项目通过 MessageBus 隔离 Telegram、QQ、CLI、IPC 等通道。标准消息至少应包含 channel、chat_id、sender_id、content、attachments 和 trace_id。

当前 Web Dashboard 直接调用 HTTP API，是本地核心功能的测试通道。后续 Telegram/QQ 不应直接调用模型，而应统一发布 inbound message，再从 outbound queue 消费回复。这样记忆、工具、审计和取消逻辑只维护一份。

## 9. 第八部分：Dashboard 与可观测性

前端位于 `frontend/`，使用 React、TypeScript、Vite、Tailwind，以及 shadcn/ui 同款的 Radix Slot、class-variance-authority、`cn()` 和 `components/ui` 组织方式。当前包含：

- 对话实验室：新建/切换会话、SSE 流式消息、停止生成、加载态和错误反馈。
- 个人记忆工作区：有效记忆、待审核候选、存储与任务三个入口；支持纠正窗口、来源跳转、向量回填、重试与撤销预览。
- 共享治理工作台：Agent 身份、空间授权、提案审核、版本沿革、撤销与审计事件；共享层按空间角色鉴权。
- 运行状态：会话、消息、记忆和任务计数，以及 turn trace、工具链和耗时。
- 工具实验台：浏览工具目录并安全验证只读工具。
- 响应式布局：桌面侧栏与窄屏纵向布局。

后端 API：

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/api/health` | 存活检查 |
| GET | `/api/overview` | 数据规模与脱敏模型状态 |
| GET/POST | `/api/sessions` | 会话列表/创建 |
| GET | `/api/sessions/{id}/messages` | 消息历史及来源消息锚点 |
| POST | `/api/sessions/{id}/chat` | 执行对话并排入后台记忆提取任务 |
| DELETE | `/api/sessions/{id}` | 删除会话及消息 |
| GET/POST | `/api/memories` | 搜索/新增记忆 |
| GET | `/api/memory-reviews` | 查询自动提取的待审核候选 |
| POST | `/api/memory-reviews/{id}/approve`、`/reject` | 批准或拒绝候选 |
| POST | `/api/memories/{id}/correct` | 带原因的版本化纠正 |
| GET | `/api/shared/memories` | 按 Agent 身份与空间权限检索生效的共享记忆 |
| POST | `/api/shared/proposals` | 在授权空间提交待审提案 |

当前 trace 已记录模型延迟、重试、token usage、工具调用链、授权决策、记忆召回计划与依据；`/metrics` 可供 Prometheus 抓取。大规模部署仍应增加集中式日志、指标长期存储和 trace 保存期限策略。

## 11. 验收方法

1. 构建前端并启动后端，访问 2237。
2. 状态页确认 main/fast/embedding 都显示模型名称且密钥为“已配置”，页面不可看到密钥原文。
3. 新建对话，发送“记住我喜欢简洁的回答”，应获得模型回复。
4. 打开「记忆 → 待审核候选」，核对模型提取的 preference、来源原话并批准；如果模型未提取，可手动添加。
5. 新开会话询问“我偏好怎样的回答”，检查已批准记忆是否被检索并影响回复；未批准候选不应参与召回。
6. 重启服务，确认会话、消息和记忆仍存在。
7. 单独创建两个 Agent 与共享空间，授权后验证提案须经 owner/curator 审核，撤权 Agent 无法读取该空间；不要使用旧聊天接口证明共享隔离。

## 12. 推荐演进顺序

已落地的能力包括流式响应、取消与会话压缩、个人记忆审核/纠正、租约任务、可选向量索引、轻量 Skills、Tool Search、MCP 客户端、受约束的 Drift、共享记忆提案治理，以及指标和浏览器回归。下一阶段若要把项目深化为多 Agent Runtime，应先为聊天、工具与来源读取建立显式 `agent_id + space_id` 上下文，再连接共享检索并扩展真实授权评测；对外主动推送、外部通道和动态插件生态仍是独立规划项。当前路线和验收口径见[项目规划说明书](./项目规划说明书.md)，最初蓝图保存在[历史归档](./archive/README.md)。

核心原则是每一阶段都维持可运行闭环，不为目录齐全而创建无法验证的抽象。

## 13. Memory Governance 与 Multi-Agent Shared Memory

`MemoryGovernance` 在同一 SQLite 数据库中使用独立表：`agents`、`spaces`、`space_grants`、`proposals`、`governed_memories`、`governance_events`。写入使用 `BEGIN IMMEDIATE`，同主题当前版本受唯一索引约束，审批采用 `expected_replaces_id` 比较当前版本，避免并发覆盖。旧个人记忆通过管理员显式导入提案，不能直接进入共享检索。

`/api/shared/*` 使用独立 `X-Agent-Key`，存储层检查 reader/contributor/curator/owner 角色；`/api/governance/*` 使用本机管理员或服务器 Token。授权检索、ID 详情、版本链、提案与事件分别执行权限检查。普通成员不能获取已撤销或过期正文；撤销当前版本还会撤销同主题历史版本。审批时重验提交者权限和旧记忆来源；来源或有效期变化也要求版本确认。

这是可独立调用的共享记忆服务，现有聊天 runtime 与其个人 `memories` 表尚未接入多 Agent 上下文。共享层当前采用词面检索，旧聊天层保留 FTS/向量/BM25 混合检索。具体 API、边界、性能样例及公开评测集接入建议见 [记忆治理与多 Agent 共享记忆](./记忆治理与多Agent共享记忆.md)。
